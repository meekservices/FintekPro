📘 FintekPro – Post-Publish Error Tracking System
Implementation Instructions for Replit Development Agent
OBJECTIVE
Implement a production-grade error tracking and observability system for FintekPro that:
Captures frontend and backend errors
Sends real-time alerts via Sentry
Persists errors internally for compliance, audit, and admin review
Provides standardized error UI for clients and agents
Enables an Admin Error Command Center
Sentry will act as a monitoring layer, while FintekPro will own the system of record.
ARCHITECTURE PRINCIPLES (NON-NEGOTIABLE)
Frontend must never write directly to database
All persistent error storage must flow through FintekPro API
Errors must be business-context aware (client, PAN, agent, transaction)
Stack traces must never be exposed to users
PAN must be masked in logs
System must support regulatory audit readiness
EPIC 1: Frontend Error Capture (React)
TASK 1.1 – Integrate Sentry (Frontend)
Install
npm install @sentry/react @sentry/tracing
Initialize in root (main.tsx / App.tsx)
Environment-aware initialization
Enable source maps
Enable performance tracing
Disable console-only logging in production
Required tags

role: client | agent | partner | admin
module: KYC | MF | AIF | PMS | Tax | Store | Portfolio
build_version

TASK 1.3 – Network & Action Error Handling
Create centralized error handler

EPIC 2: Backend Error Gateway (MANDATORY)
TASK 2.1 – Create Error Ingestion API
Endpoint
POST /api/errors/ingest
Payload contract
{
  "source": "frontend | backend | webhook",
  "severity": "info | warning | error | critical",
  "error_code": "STRING_ENUM",
  "message": "Human readable",
  "stack": "Optional",
  "context": {
    "module": "KYC",
    "client_id": "UUID",
    "agent_id": "UUID",
    "transaction_id": "UUID",
    "pan": "MASKED"
  }
}
Validation
Enforce enum values
Mask PAN server-side
Reject oversized stack payloads
TASK 2.2 – Persist Errors (Error Ledger)
Create table: error_ledger
Required columns:
id (UUID)
timestamp
severity
source
error_code
module
message
stack_hash
client_id (nullable)
agent_id (nullable)
pan_masked
transaction_id
sentry_event_id
status (open | acknowledged | resolved)
environment (dev | staging | prod)
TASK 2.3 – Backend Sentry Integration
Capture unhandled exceptions
Capture API failures
Attach request context
Link sentry_event_id to DB record
TASK 2.4 – Alerting Rules
Trigger alerts when:
Severity = critical
Same error repeats > X times in Y minutes
Payment / KYC / Order placement fails
Send alerts to:
Admin email
Slack / webhook (configurable)

EPIC 6: Environment & Security Controls
Enable Sentry only in staging & prod
Mask sensitive fields
Configurable sampling rate
Role-based access to error data
Disable error ingestion endpoint for unauthenticated public access
ACCEPTANCE CRITERIA (FINAL CHECK)
❏ Errors visible in Sentry within seconds
❏ Same error visible in Admin Error Command Center
❏ PAN never stored in plain text
❏ User never sees stack trace
❏ Admin can mark error resolved
❏ Critical failures trigger alerts
FINAL NOTE FOR REPLIT AGENT
Treat Sentry as a diagnostic tool, not the source of truth.
FintekPro must retain ownership of error data, compliance, and operational intelligence.
