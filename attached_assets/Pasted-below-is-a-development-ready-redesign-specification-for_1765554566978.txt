below is a development-ready redesign specification for the page
/mutual-funds to support regulatory-compliant execution of client buy and sell orders from client portfolio holdings.
This spec is written for your Replit developers and product owners. It covers:
Purpose & scope
UX/UI layout & wireframe guidance
User journeys (Buy / Sell) with step-by-step UI screens
Regulatory and compliance checks required before execution
Backend APIs, DB changes, and event flows
Audit, logging, and reconciliation rules
Error handling, safeguards, and testing checklist
Use this as the single-source handoff to implement the feature.
1. PURPOSE & SCOPE
Goal: Modify /mutual-funds page so an advisor/retail client (depending on permissions) can place Buy and Sell mutual fund orders directly from the client’s portfolio in a way that meets regulatory requirements (KYC, suitability, consent, transaction logging, reconciliation, settlement).
Scope:
Only regular/direct plan enforcement handled elsewhere — this page must honor plan type.
Enable order placement (buy / sell/ SIP / STP) for schemes that are supported for on-platform execution.
Enforce pre-trade checks: KYC status, FATCA/PEP/AML, bank mandate (mandate for redemption payout), consent / mandate for SIP/Investor OTP if required.
Support order lifecycle: created → placed → confirmed → settled → reconciled.
Provide clear UI prompts for users, and an admin/audit view for compliance team.
Audience: Frontend developers, backend engineers, QA, compliance team.
2. HIGH-LEVEL UX CHANGES (Page Overview)
Replace current /mutual-funds page with a two-column, action-oriented interface:
Top-level layout (desktop):
Left column (40%): Client Portfolio (holdings list + quick filters)
Right column (60%): Action Panel (Buy / Sell flow UI + scheme details + validations)
Global header remains: Client selector (if advisor has multiple clients)
Floating bottom bar: “Active Orders / Notifications”
Mobile: Collapsible panels — Portfolio (accordion) → Tap opens Action Panel.
Key new elements:
Portfolio Holdings Table (with ACH/mandate status, current NAV, qty, folio)
Scheme Detail Panel (Full scheme info, suitability tag, regulatory flags)
Action Tabs: [Buy] [Sell] [SIP] [STP] — each opens guided form
Pre-Trade Checklist Widget (KYC, Bank Mandate, AML status, Suitability)
Order Preview Modal (shows charges, tax implication, settlement timeline)
Consent / eSign (if required) modal with audit capturing
3. USER JOURNEYS & UI FLOW
Below are step-by-step journeys for the two primary flows (Buy & Sell). Each step includes UI components and validations.
3.1 Shared prerequisite: Client selection
Top-left: Client selector dropdown (advisor only). Default → current logged client.
When client selected, page fetches: holdings, KYC status, bank mandates, risk profile, folios.
APIs called:
GET /clients/{id}/holdings
GET /clients/{id}/kyc
GET /clients/{id}/bank-mandates
GET /clients/{id}/risk-profile
3.2 BUY ORDER FLOW (from client portfolio page)
User action:
Click [Buy] on Action Panel OR click [Buy More] button in the holdings table.
UI Step 1 — Scheme Selection
Search box with autocomplete (by scheme name/ISIN/AMC).
Show only schemes allowed (plan_type filter).
Show small badges: “Regular”, “Direct”, “SIP Eligible”, “Execution Allowed”.
UI Step 2 — Order Form
Fields:
Order Type: Lumpsum / SIP
Amount (₹) or Units (if allowed)
Bank Mandate Payment Method: Netbanking / UPI / Mandate (NACH/One-Time Mandate)
Execution Mode: Market NAV (Default) / Special NAV (if applicable)
Folio (select existing folio or create new)
Adviser Fee / Broker tag (if applicable; must be pre-configured)
Compliance Notes (optional)
Real-time validations:
Check client KYC status → if KYC not verified => block with CTA “Complete KYC”
Check FATCA/PEP/AML flags → if flagged => route to compliance + block
Check bank mandate: for NACH/mandate-based payments, if not present, present flow to create mandate.
Suitability check: compare scheme risk vs client risk profile — if mismatch, show prominent warning and require affirmation checkbox (“I confirm client approves”).
UI Step 3 — Pre-Trade Checklist (left side)
KYC: Verified / Not Verified
Bank Mandate: Present / Not Present
AML: Clean / Flagged
Risk Suitability: Match / Mismatch
Blockers displayed in red; soft-warnings in amber. Soft-warnings require a checkbox confirmation; blockers prevent order.
UI Step 4 — Order Preview Modal
Display:
Order details (Scheme, Amount/Units, Folio, Bank Method)
Expected NAV cutoff (if intra-day) and expected settlement timeline
Charges: Platform Fee, Transaction Charges, GST
Taxes if applicable (e.g., taxes on purchase not applicable but shown)
Refund/Cancel policy
Unique order reference (FTX-MF-BUY-{timestamp})
CTA: [Confirm & Place Order] or [Cancel]
Execution
On Confirm: POST /orders/mf
Payload includes: client_id, scheme_id, folio_id, order_type, amount, payment_method, adviser_id, compliance_ack
Backend returns immediate ack: {order_id, status: PENDING_SUBMISSION}
Then platform calls: payment gateway / NACH flow / AMC API / Registrar API depending on payment method.
Update status to SUBMITTED → AWAITING_CONFIRMATION → COMPLETED or REJECTED.
Post-Execution
Display order status on page; send email/SMS to client and advisor.
Auto-sync with portfolio once confirmation received from RTA/AMC (units allotted).
Generate contract note and record in audit logs.
3.3 SELL (REDEMPTION) FLOW (from client portfolio holding)
User action:
Click [Sell / Redeem] against a holding row in the portfolio table.
UI Step 1 — Redemption Form
Show:
Current holding details: Folio, Units, NAV, Last NAV date, Minimum redemption amount/units, Exit Load
Present a compute box: Enter units or amount to redeem → auto-calc counterpart (units/amount) and resulting remaining holding.
Pre-Trade Validations (must pass):
KYC Verified (PAN KYC)
Bank mandate present for payout (bank account mapped to folio); if not present, present “Add Bank” flow (mandate setup) or require offline documentary proof.
Lock-in or exit load check (if within lock-in, disallow or warn)
Pledged / lien check (if pledged, block and show steps for release)
AML / Sanction list check
Minimum residual units/amount checks as per AMC rules
UI Step 2 — Tax & TDS Considerations
Show if redemption attracts TDS (for NRIs etc.) — require tax declaration.
If client is NRI or specified person, require additional fields per AMC/Registrar.
Offer option to provide PAN if missing (if required).
UI Step 3 — Order Preview (similar to Buy)
Show expected payout date (T+N), exit load, taxes, applicable TDS, net payout estimate.
Confirm redemption and payout bank (preselected mapped bank). Allow editing only if valid.
Execution
On Confirm: POST /orders/mf/redeem
Payload: client_id, folio_id, scheme_id, units_or_amount, payout_bank_id, tax_declaration, adviser_id.
Backend: trigger RTA/AMC redemption API OR generate/distribute offline redemption instruction (depending on integration).
Order status tracked: PENDING_SUBMISSION → SUBMITTED → PROCESSED → SETTLED.
If instant redemption option (liquidity fund same-day), handle accordingly.
Settlement & Reconciliation
Once units debited and payout triggered, reconciliation engine tags payout entries in escrow/ledger.
Admin UI: Settlement Tracker shows step-by-step status (like earlier spec).
4. REGULATORY & COMPLIANCE REQUIREMENTS (Pre-Trade & Post-Trade)
Implement the following checks and capture evidence before any trade can be executed:
Pre-trade mandatory checks:
KYC / CKYC status: block unless verified.
PAN verified / name match with folio – block if mismatch.
AML / sanctions screening – if flagged route to compliance and block.
Risk profiling / suitability: if scheme risk > client risk and client not suitable, require explicit client acknowledgment with stored consent.
Bank mandate / payout bank: must be validated for redemptions. For purchases via NACH mandate, ensure mandate active.
Mandate / E-mandate / UPI mandate flows for SIP purchases — include OTP capture when required.
Pledge / Lien check: block redemption if pledged.
Exit load / lock-in check: warn & block if redemption violates lock-in.
TDS / FATCA capture: collect necessary tax declarations at redemption when required.
Post-trade & Reporting:
Contract note must be generated and delivered to client within statutory timeline.
Audit trail for each human action: who, what, when, IP. Store for 7 years.
Reconciliation between AMC/RTA confirmations and internal ledger.
Mis-sell prevention: store client acknowledgement for suitability exceptions.
Suspicious transaction reporting: flag large redemptions/ off-pattern activity for compliance review.
5. BACKEND API & DATA MODEL CHANGES
Below are recommended endpoints, payloads, and DB updates.
5.1 New/Updated API endpoints
Client/Portfolio
GET /clients/{clientId}/holdings
GET /clients/{clientId}/folios
GET /clients/{clientId}/kyc
GET /clients/{clientId}/bank-mandates
POST /clients/{clientId}/bank-mandates (to add)
Order lifecycle
POST /orders/mf — create buy order
payload: {client_id, scheme_id, folio_id, amount, units, order_type, payment_method, adviser_id, compliance_ack}
response: {order_id, status}
POST /orders/mf/redeem — create sell order
payload: {client_id, folio_id, scheme_id, units_or_amount, payout_bank_id, tax_declaration, adviser_id}
GET /orders/{orderId} — order status
GET /orders?client_id= — list client orders
POST /orders/{orderId}/cancel — cancel order
Webhook endpoint: POST /webhooks/rtaconfirmation — RTA/AMC confirmation for order status update
POST /orders/{orderId}/confirm-otp — for mandates/UPI/OTP confirmations where required
Admin/Compliance
GET /admin/orders/pending
POST /admin/orders/{orderId}/override — require reason & audit log
GET /admin/reconciliation/{date-range}
5.2 Database updates (suggested)
Tables (add/augment):
orders_mf (order_id PK, client_id, adviser_id, scheme_id, folio_id, type, amount, units, status, created_by, created_at, updated_at, compliance_flags JSON)
holdings (existing) — add fields: pledge_status, last_nav_date, exit_load_applicable boolean, lock_in_end_date
bank_mandates (mandate_id, client_id, bank_account, mandate_type, status, created_at)
order_audit_log (order_id, action, actor_id, role, timestamp, ip, notes)
reconciliation_entries (order_id, rta_reference, status, settled_amount, settled_date)
contract_notes (order_id, pdf_url, generated_at)
suitability_acknowledgements (order_id, client_id, adviser_id, ack_text, signature_type, timestamp)
Store all raw RTA/AMC responses in rta_raw_responses for audit.
6. AUDIT, LOGGING & DATA RETENTION
Log every action (UI click that leads to an order) in order_audit_log.
Keep RTA/AMC confirmations and raw webhooks for audit (7 years).
Generate contract note PDF and store S3 URL & hash in DB.
Capture IP, user agent, and actor role for each action.
All suitability confirmations must persist with timestamp and unique order reference.
7. UI ACCESS CONTROL & RBAC
Roles: Admin, Advisor, Client (self-service), Compliance.
Advisors can create orders only for their assigned clients.
Only Admin/Compliance can override blocked orders; overrides must record reason & create ticket.
Clients can place buy/sell orders for their own folios if page allows self-service with OTP confirmation.
8. ERROR HANDLING & EDGE CASES
Payment failure (on buy): show clear error, store order as FAILED_PAYMENT, allow retry.
RTA rejects (unit allocation failure): store REJECTED state with RTA message, notify adviser & client, create auto-ticket.
Partial fills (rare for MF): if partial allotment occurs, ensure reconciliation entries reflect partial and platform charges adjust.
Connectivity to banks/AMC down: queue order for retry and show “Pending due to external service” with ETA.
Pledge/Freeze detected: block and surface changes to client with instructions to release pledge.
